## 🏗️ 2. Архитектура и Конфигурация Сервера

### 📂 Пути и Директории
*   **Корневая директория сайта на сервере:** `/var/www/quete`
*   **Конфигурационный файл окружения:** `/var/www/quete/.env`
    *   *Важно:* Файл `.env` на сервере содержит настройки продакшна. Не перезаписывайте его локальным файлом напрямую! Вместо этого точечно обновляйте параметры через SFTP.
    *   Критически важные параметры боевого `.env`:
        ```env
        WS_CLIENT_HOST=quete.ru
        WS_CLIENT_PORT=8888
        WS_PORT=8080
        WS_HOST=127.0.0.1
        ```

### 🌐 Сетевая Архитектура и Проксирование
1.  **Nginx:**
    *   Конфигурация Nginx настроена на проксирование WebSocket.
    *   Nginx принимает внешние безопасные SSL-подключения на порту **`8888`** (адрес `wss://quete.ru:8888`) и перенаправляет трафик локально на внутренний порт **`8080`**.
2.  **WebSocket-Сервер (Ratchet PHP):**
    *   Запущен локально на интерфейсе `127.0.0.1` и слушает порт **`8080`** (`ws://127.0.0.1:8080`).
    *   Сервер запущен как системная служба systemd: `quete-websocket.service`.

### 🛡️ Системный Брандмауэр (UFW)
*   Внешний порт `8888/tcp` открыт для входящих WSS-подключений клиентов.
*   Внутренний порт `8080/tcp` закрыт для внешней сети в целях безопасности и доступен только локально.

## 🛠️ 3. Каталог Скриптов в папке `scratch/`

Папка `scratch/` содержит утилиты автоматизации, которые вы должны использовать для управления сервером и проверки кода:

| Скрипт | Описание | Когда запускать |
| :--- | :--- | :--- |
| **`deploy_updated_code.py`** | Основной скрипт деплоя кода. Загружает файлы из списка `files_to_upload`, проверяет/обновляет `.env` на сервере, выполняет `systemctl daemon-reload` и перезапускает `quete-websocket` и `nginx`. | После внесения любых изменений в PHP, JS или CSS файлы. |
| **`deploy_images.py`** | Специфический скрипт деплоя изображений. Загружает файлы из `assets/img/` на сервер, выставляет владельца `www-data:www-data`, права `755` и перезапускает Nginx. | При добавлении или обновлении графических ресурсов. |
| **`compare_files.py`** | Подключается к VPS и сравнивает sha256-хэши локальных файлов из списка с файлами на сервере, выводя список различий. | Перед деплоем для понимания, какие файлы реально изменились. |
| **`find_modified.py`** | Сканирует локальную рабочую директорию и выводит файлы, измененные за последние 24 часа (исключая `vendor` и `.git`). | Для быстрого поиска файлов, отредактированных другими агентами или пользователем. |
| **`check_vps_logs.py`** | Подключается по SSH и выводит последние 50 строк логов службы `quete-websocket` из `journalctl`, а также ошибки Nginx из `/var/log/nginx/error.log`. | При жалобах на падение сокета, ошибках соединения или при диагностике сбоев. |
| **`check_firewall.py`** | Проверяет текущий статус брандмауэра UFW на сервере и доступность порта 8888. | При проблемах с сетевым подключением к WebSocket. |
| **`fix_firewall.py`** | Выполняет на сервере команду `ufw allow 8888/tcp` для открытия порта WebSocket. | Если `check_firewall.py` показывает, что порт 8888 закрыт. |
| **`optimize_images.py`** | Локально сжимает и оптимизирует графические ресурсы в `assets/img/` с использованием Pillow. | При добавлении новых тяжелых изображений в проект перед их отправкой на сервер. |
| **`check_xss.py`** | Локальный сканер безопасности. Ищет небезопасное использование свойства `.innerHTML` во всех JavaScript файлах проекта. | Перед коммитом/деплоем нового JavaScript-кода для предотвращения XSS-уязвимостей. |

## 🔄 4. Регламент и Пошаговый Процесс Деплоя

При выполнении задач по обновлению сайта строго следуйте следующему алгоритму:

### Шаг 1: Поиск локальных изменений
Запустите скрипт `find_modified.py` для определения файлов, над которыми велась работа в локальном окружении:
```bash
python scratch/find_modified.py
```

### Шаг 2: Сравнение с сервером
Запустите `compare_files.py` для точной сверки локального состояния с удаленным сервером:
```bash
python scratch/compare_files.py
```

### Шаг 3: Проверка ограничений (Важно!)
В соответствии с правилами **`GEMINI.md`**:
*   Категорически запрещено изменять `.sql` файлы и файл ядра `core/ai_handler.php` без прямого согласования с пользователем.
*   Если вы обнаружили локальные изменения в `core/ai_handler.php`, убедитесь, что они были одобрены пользователем, прежде чем деплоить их. Вы можете использовать `scratch/diff_ai_handler.py` для просмотра конкретных изменений в этом файле.

### Шаг 4: Выполнение деплоя кода
Если изменялся только код (PHP, JS, CSS), откройте скрипт `scratch/deploy_updated_code.py`, убедитесь, что все измененные файлы перечислены в массиве `files_to_upload`, и запустите его:
```bash
python scratch/deploy_updated_code.py
```
Скрипт автоматически:
1. Загрузит файлы на сервер.
2. Проверит `.env` на наличие переменной `WS_CLIENT_PORT=8888`.
3. Перезапустит веб-сервер и службу WebSocket Ratchet.
4. Выведет статусы служб.

### Шаг 5: Выполнение деплоя изображений (при наличии изменений в графике)
Если вы оптимизировали или добавили новые изображения в `assets/img/`, запустите:
```bash
python scratch/deploy_images.py
```
Это перенесет изображения статики, сбросит права доступа на сервере на `www-data` и обновит кэш Nginx.

### Шаг 6: Проверка логов службы после деплоя
Всегда проверяйте, что служба WebSocket запустилась успешно и в ней нет ошибок:
```bash
python scratch/check_vps_logs.py
```

### Шаг 7: Ведение журнала работ
После успешной проверки работы обновленного функционала обязательно обновите файл `COMPLETED_WORK.md` в корне проекта, подробно описав внесенные изменения на русском языке.

## 🚀 5. Использование SSH MCP-Сервера (Интерактивное управление)

Если в вашей рабочей среде настроен и включен **SSH MCP-Сервер** (`ssh-mcp`), вы можете выполнять команды администрирования на VPS напрямую через встроенные инструменты сопряжения, минуя необходимость запуска локальных Python-скриптов.

### Примеры интеграционных возможностей:
1. **Выполнение команд напрямую:** Вы можете запрашивать статус демона сокетов или перезапуск nginx:
   ```bash
   # Выполнить на сервере через инструмент ssh-mcp:
   systemctl status quete-websocket.service
   systemctl restart quete-websocket.service
   systemctl restart nginx
   ```
2. **Просмотр логов в реальном времени:**
   ```bash
   journalctl -u quete-websocket.service -n 50 -f
   ```
3. **Безопасное редактирование:** Вы можете просматривать или вносить точечные правки в боевой файл `/var/www/quete/.env` без ручного копирования через SFTP.

> [!WARNING]
> При использовании прямого терминального доступа через MCP строго соблюдайте ограничения **`GEMINI.md`**. Не редактируйте системные и ядерные файлы в обход согласования, не производите разрушительных действий на сервере (`rm -rf` на важные директории и т.д.).
